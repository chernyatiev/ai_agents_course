# Занятие 4. Банк задач

Референс: [s12 — Task System](https://learn.shareai.run/en/s12/) (записи в файлах,
статусы, жизнь между сессиями) и идея оглавления в промпте из
[s09 — Memory](https://learn.shareai.run/en/s09/).

**`messages` живёт до `/reset` или выхода, банк — остаётся.** У агента появляется
состояние вне контекста модели. Цикл при этом **не меняется вообще**: всё новое —
это инструменты, файлы на диске и команды REPL.

```
ты> Придумай задачу на остатки для 6 класса, проверь и сохрани
  list_problems → z3_check → save_problem
агент> Сохранено как P-0001, статус verified.

$ uv run agent            # новый запуск: messages пуст, а банк на месте
ты> Какие задачи для 6 класса уже есть?
  list_problems → P-0001 [verified] Наименьшее число с остатками 3 и 4
```

Вторая идея продолжает занятие 3: **у модели и человека разные права**. Модель
предлагает и проверяет задачи, а утвердить задачу может только преподаватель. У модели
такой возможности нет: в коде просто отсутствует инструмент, который ставит `approved`.

## Жизненный цикл задачи

```
draft ──(harness перепроверил)──▶ verified ──(/approve)──▶ approved
  ▲                                  │                          │
  └─────────── любое изменение задачи сбрасывает статус ─────────┘
           /reject <id> <причина> → rejected (комментарий видит модель)
```

| Кто | Что может |
| --- | --- |
| **Модель** | `list_problems`, `get_problem`, `save_problem` (новая задача или изменение существующей) |
| **Harness** | ставит `verified` или `draft`, сам перезапуская проверку |
| **Преподаватель** | `/approve`, `/reject`; подтверждает перезапись задачи |

## Проверка, которую можно воспроизвести

Модель *утверждает*, что проверила ответ. Harness не верит на слово: `save_problem`
получает проверочный вызов (`verification`) и **сам запускает его ещё раз** тем же
путём, что и обычный вызов модели: разрешения → реестр → песочница
(`src/agent/verify.py`). Статус `verified` ставится, только если:

- результат совпадает с `answer`;
- для `z3_check` решение единственно (`unique: true`), для `sympy_solve` ровно одно.

Проверять можно через `python_eval`, `sympy_solve` и `z3_check`. `python_run` не
подходит: каждый запуск скрипта требует подтверждения, а проверка при сохранении
идёт без вопросов.

## Формат записи: `bank/P-0001.json`

```json
{
  "id": "P-0001",
  "title": "Остатки 3, 4, 5",
  "grade": 6,
  "topic": "делимость",
  "statement": "Найдите наименьшее натуральное n > 1, которое при делении на 3, 4 и 5 даёт остаток 1.",
  "answer": {"n": 61},
  "solution": "n − 1 делится на НОК(3, 4, 5) = 60, значит n = 61.",
  "verification": {
    "tool": "z3_check",
    "arguments": {"variables": {"n": "Int"}, "constraints": ["n > 1", "n % 3 == 1", "n % 4 == 1", "n % 5 == 1"], "minimize": "n"},
    "result": {"status": "sat", "solution": {"n": 61}, "objective_value": 61, "unique": true},
    "ok": true,
    "reason": "ответ совпадает с решением z3, решение единственно",
    "checked_at": "2026-11-17T12:00:00"
  },
  "status": "verified",
  "review": null,
  "created_at": "2026-11-17T12:00:00",
  "updated_at": "2026-11-17T12:00:00"
}
```

Почему один файл на задачу, как `.tasks/` в s12: его можно прочитать глазами, `git diff`
показывает, что изменилось, а испорченный файл ломает одну задачу, а не весь банк.
Запись атомарная: сначала временный файл, потом `os.replace`.

## Инструмент, которым нельзя навредить

**Модели передаётся id, а не путь к файлу.** Путь строит `bank.py`, id проверяется по
формату `P-\d{4}`, поэтому `../.env` не пройдёт. Сценарий «запись вне `bank/`» не нужно
ловить разрешениями: он невозможен.

- В схеме `save_problem` нет поля `status`. Если модель передаст `"status": "approved"`,
  реестр вернёт `Ошибка TypeError`.
- Инструментов удаления и утверждения нет. Это команды преподавателя.
- Новая задача сохраняется без вопроса, а **перезапись** (`save_problem` с `id`) —
  новое правило в `permissions.RULES`, требующее подтверждения.

## Оглавление банка в системном промпте

Перед каждым ходом `main.py` обновляет системный промпт: в конец добавляется строка
вида «Задач в банке: 3 (verified: 2, approved: 1). По классам: 6 кл — 2, 7 кл — 1.
Темы: делимость, логика.» Так модель знает, что уже есть, а полный текст задачи
читает через `get_problem`. Сам цикл (`loop.py`) не меняется.

## Разрешения «всегда» сохраняются

Ответ `a` на вопрос о разрешении записывается в `.agent/settings.json` и действует
после перезапуска, как правила `allow` в `.claude/settings.json` у Claude Code.
Это удобно, но и опасно: разрешение, данное вчера, действует сегодня. Посмотреть их —
`/permissions`, забыть — `/forget`. Испорченный файл настроек игнорируется.

## Запуск

```bash
cd lesson04
cp ../lesson03/.env .env      # или cp .env.example .env и заполнить
uv run agent -v
uv run --group dev pytest     # 113 тестов, сеть не нужна (~20 с)
```

Банк хранится в `lesson04/bank/`, настройки — в `lesson04/.agent/`. Обе папки в
`.gitignore`. Другую папку банка можно задать переменной `BANK_DIR`.

Команды REPL:

| Команда | Что делает |
| --- | --- |
| `/bank [статус]` | задачи в банке, можно отфильтровать по статусу |
| `/show <id>` | полная запись: условие, ответ, решение, проверка, отзыв |
| `/approve <id>` | утвердить задачу (только из `verified`) |
| `/reject <id> <причина>` | отклонить с комментарием для модели |
| `/permissions`, `/forget` | сохранённые разрешения: посмотреть, забыть |
| `/tools`, `/mode`, `/messages`, `/reset`, `/exit` | как в занятии 3; `/reset` очищает только историю |

## Демо

Сценарии 1–3 проверены с настоящей моделью.

1. **Сохранить и найти после перезапуска.** «Придумай задачу на остатки для 6 класса
   с единственным ответом, проверь и сохрани в банк.» Модель вызывает `list_problems`,
   `z3_check`, `save_problem` → `verified`. Выйти (`/exit`), запустить снова и спросить
   «Какие задачи для 6 класса уже есть в банке?».
2. **Отзыв преподавателя.** `/reject P-0001 Слишком просто: добавь ещё два делителя`,
   затем «Исправь задачу P-0001 по замечанию преподавателя». Модель читает отзыв через
   `get_problem`, решает заново, на перезапись появляется `⚠ Перезапись задачи в банке`,
   после `y` задача снова `verified`.
3. **Утверждение.** `/show P-0001`, `/approve P-0001`, `/bank approved`.
4. **Неверный ответ не пройдёт.** Тест показывает, что задача с ответом 60 при проверке,
   дающей 61, остаётся `draft`: `uv run --group dev pytest -k wrong_answer -v`.
5. **Мост к занятию 5.** `uv run --group dev pytest -k formalization -v`: в условии
   «остаток 2», в формализации z3 «остаток 1» — и задача получает `verified`.
   **verified значит «формализация воспроизводит ответ», а не «формализация
   соответствует условию».**

### Почему поменялась песочница
В занятии 3 каждый вызов `python_eval`, SymPy и z3 запускал новый интерпретатор
(`spawn`), который заново импортировал sympy и z3: **~1,8 с на вызов**. Банк
перепроверяет ответ при каждом сохранении, и это стало заметно. Теперь на macOS и Linux
используется `forkserver`: сервер один раз импортирует `agent.tools`, а каждый вызов —
быстрая копия (fork) этого процесса. Первый вызов по-прежнему ~1,7 с, следующие ~0,01 с.
Изоляция та же: отдельный процесс с таймаутом. В Windows остаётся `spawn`.

## Известные ограничения (задел на следующие занятия)

- `verified` не ловит ошибку формализации (демо 5) → **занятие 5**, независимый проверяющий.
- Оглавление в промпте растёт вместе с банком. На сотнях задач понадобятся поиск и
  сжатие контекста (s08, s09).
- Один пользователь, один процесс: блокировок файлов нет, два агента над одним банком
  могут выдать одинаковый id.
- Нет поиска дубликатов: модель полагается на `list_problems` (упражнение 2).
- Нет лимита шагов цикла → **занятие 8**.
- Как и в занятии 3: если вызываете `run_turn` из своего скрипта, оберните запуск в
  `if __name__ == "__main__":`, иначе дочерние процессы песочницы будут перезапускать
  ваш скрипт.
