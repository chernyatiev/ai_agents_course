# План занятия 4. Банк задач

Код занятия: `lesson04/`. Референс: [s12 — Task System](https://learn.shareai.run/en/s12/),
дополнительно идея оглавления из [s09 — Memory](https://learn.shareai.run/en/s09/).
Продолжительность: 2 академических часа (90 мин).

## Цель
Студенты понимают, что состояние агента не обязано жить в контексте модели, и
проектируют хранилище так, чтобы права модели, harness и человека были разделены
кодом, а не промптом.

## Результаты занятия
После занятия студент умеет:
1. Объяснить разницу между историей `messages` и состоянием на диске.
2. Спроектировать запись (поля, статусы) и таблицу «кто что может менять».
3. Сделать инструмент записи, который принимает id, а не путь.
4. Перепроверять утверждение модели в harness, а не верить ему.
5. Объяснить, почему `verified` ещё не значит «задача правильная».

## Ход занятия

### 1. Мотивация (10 мин)
- В `lesson03` придумать задачу, выйти через `/exit`, запустить снова и спросить о ней.
  Задачи нет: вся «память» агента — это `messages`.
- Вопрос аудитории: где должна жить задача, которую преподаватель утвердил вчера?
- Связать с s12: TodoWrite (s05) живёт в сессии, Task System — в файлах `.tasks/`.

### 2. Модель данных и статусы (15 мин)
- Формат `bank/P-0001.json`, разбор полей (см. README занятия).
- Статусы: `draft → verified → approved`, `rejected` с комментарием; любое изменение
  сбрасывает утверждение.
- Таблица прав:

  | Кто | Что может |
  | --- | --- |
  | Модель | `list_problems`, `get_problem`, `save_problem` |
  | Harness | ставит `verified` / `draft` после повторной проверки |
  | Преподаватель | `/approve`, `/reject`, подтверждает перезапись |

- Обсудить: почему `approved` нельзя дать модели, даже «с подтверждением»?

### 3. Хранилище `bank.py` (15 мин)
- Один файл на запись. Почему не один большой `bank.json`: diff, порча одного файла.
- Атомарная запись: временный файл → `os.replace`. Что будет без неё при падении.
- **Id вместо пути.** `_path()` строит путь сам и проверяет формат `P-\d{4}`.
  Показать тест `test_bad_ids_rejected` с `../.env`.
- Главная мысль: самое надёжное разрешение — инструмент, которым нельзя сделать
  опасное. Запись вне `bank/` не нужно ловить правилом, она невозможна.

### 4. Проверка, которую можно воспроизвести: `verify.py` (20 мин)
- Модель *утверждает*, что проверила. `save_problem` получает этот проверочный вызов и
  **запускает его заново** через разрешения → реестр → песочницу.
- `matches()`: своё правило для каждого инструмента; для z3 обязательно `unique: true`.
- Тесты-иллюстрации: `test_wrong_answer_stays_draft` (ответ 60 при проверке 61),
  `test_not_unique_stays_draft`, `test_verification_goes_through_permissions`
  (эксплойт из занятия 3, спрятанный в проверке, останавливают ворота 1).
- Почему `python_run` не годится для проверки: каждый запуск требует подтверждения.
- Попутно — песочница стала быстрее: `forkserver` с предзагрузкой вместо `spawn`
  (1,8 с → 0,01 с на вызов). Повод поговорить о цене изоляции.

### 5. Человек в контуре и разрешения на диске (10 мин)
- `/approve` только из `verified`, `/reject` с комментарием, который модель читает через
  `get_problem`.
- Новое правило в `RULES`: перезапись задачи → спросить.
- Ответ `a` теперь сохраняется в `.agent/settings.json` (обещано в занятии 3).
  Обсудить риск: вчерашнее «всегда» действует сегодня. `/permissions`, `/forget`.

### 6. Живое демо (15 мин)
Сценарии 1–3 проверены с настоящей моделью.
1. «Придумай задачу на остатки для 6 класса с единственным ответом, проверь и сохрани
   в банк.» → `list_problems`, `z3_check`, `save_problem` → `verified`.
   `/exit`, новый запуск, «Какие задачи для 6 класса уже есть в банке?».
2. `/reject P-0001 Слишком просто: добавь ещё два делителя`, затем «Исправь задачу
   P-0001 по замечанию преподавателя». Модель читает отзыв, решает заново, появляется
   `⚠ Перезапись задачи в банке`, после `y` — снова `verified`.
3. `/show P-0001`, `/approve P-0001`, `/bank approved`. Открыть сам файл
   `bank/P-0001.json` в редакторе.
4. `uv run --group dev pytest -k wrong_answer -v` — неверный ответ остаётся `draft`.

### 7. Пределы и мост к занятию 5 (5 мин)
- `uv run --group dev pytest -k formalization -v`: в условии «остаток 2», в z3
  «остаток 1», статус **verified**.
- Вывод: `verified` значит «формализация воспроизводит ответ», но не «формализация
  соответствует условию». Сама модель и формализует, и проверяет — нужен независимый
  проверяющий (**занятие 5**).
- Другие ограничения: оглавление растёт с банком (s08/s09), нет блокировок файлов,
  нет поиска дубликатов, нет лимита шагов (занятие 8).

## Домашнее задание
`lesson04/EXERCISES.md`:

- «Перенеси на свой агент»: формат записи и статусы в `SPEC.md`, хранилище с
  атомарной записью, инструмент без путей, перепроверка утверждения модели.

Критерий готовности: данные агента переживают перезапуск, модель не может записать
файл вне своей папки и не может поставить «финальный» статус, всё проверено тестами
без сети.
