# План занятия 3. Песочница и разрешения

Код занятия: `lesson03/`. Референс: [s03 — Permission](https://learn.shareai.run/en/s03/).
Продолжительность: 2 академических часа (90 мин).

## Цель
Студенты понимают, что harness обязан проверять каждый вызов инструмента **до**
выполнения, и различают два слоя защиты:

- **разрешения** решают, *можно ли* выполнять вызов (deny → ask → allow);
- **песочница** ограничивает, *что может натворить* разрешённый вызов (процесс, таймаут, лимиты).

Ключевой тезис из референса: безопасность нельзя строить на доверии к модели, её обеспечивает код.

## Результаты занятия
После занятия студент умеет:
1. Объяснить, почему пустой `__builtins__` в `eval` не является песочницей.
2. Встроить проверку разрешений в цикл агента, не меняя его структуру.
3. Написать правило deny и правило ask и покрыть их тестами без сети и клавиатуры.
4. Запустить код модели в отдельном процессе с таймаутом.
5. Назвать, что такая защита *не* гарантирует.

### 2. Главная идея: одна вставка в цикл (10 мин)
Показать diff `lesson02/src/agent/loop.py` → `lesson03/src/agent/loop.py`:
```python
decision = permissions.check(name, arguments, ask=ask)  # ← занятие 3
if decision.allowed:
    result = tools.call(name, arguments)
else:
    result = f"Отказано: {decision.reason}"
```
- Отказ, как и ошибка в занятии 2, — это *данные для модели*: она может сменить подход.
- `ask` передаётся параметром, как `chat`: тесты не ждут клавиатуру.

### 3. Конвейер разрешений: `permissions.py` (25 мин)
Разбор по воротам, с кодом на экране:

| Ворота | У нас | Совпало → |
| --- | --- | --- |
| 1. Deny | `find_violation`: AST-обход, запрет `_атрибутов`, `BANNED_NAMES`, строк с `__`, import вне `ALLOWED_MODULES` | отказ |
| 2. Rules | `RULES`: `python_run` всегда; таймаут > 5 с; константа > 10⁷ | ворота 3 |
| 3. Ask | `y / N / a` (a — «всегда» до `/reset`) | allow / deny |

Акценты:
- **Порядок важен**: deny проверяется первым и действует в любом режиме, даже после ответа `a`.
- **AST, а не подстроки.** В референсе честно сказано, что поиск подстроки ненадёжен.
  Показать, как `'{0.__class__}'.format(())` и `f'{().__class__}'` ловятся через `ast.Constant` и `ast.Attribute`.
- **Отказ по умолчанию**: пустой ответ, EOF и отсутствие `ask` означают deny.
- **Режимы** `default / auto / strict` и сравнение с permission modes Claude Code.
- Блок «Dive into CC»: в Claude Code четыре исхода (`allow`, `deny`, `ask`, `passthrough`).
  У нас `evaluate()` возвращает три, а `check()` сводит их к двум.

### 4. Песочница: `sandbox.py` (15 мин)
- `run_isolated(func, kwargs, timeout)`: `multiprocessing` со `spawn`, тип ошибки сохраняется.
  Подключается одним параметром: `register(..., timeout=5)`. Цикл и инструменты не меняются.
- `run_python(code, timeout)` для нового инструмента `python_run`: `python -I`, `env={}`,
  временная папка, обрезка вывода.
- `resource.setrlimit`: CPU, размер файлов, память. Честно: в macOS `RLIMIT_AS` не работает,
  в Windows есть только таймаут.
- Предупреждение: это учебная песочница. Настоящая изоляция — контейнер, nsjail/gVisor, ВМ.

### 5. Живое демо (15 мин)
1. `uv run agent -v`: «Сколько шестизначных чисел, у которых сумма первых трёх цифр
   равна сумме последних трёх? Проверь перебором скриптом.» Появляется `⚠ Запуск скрипта Python`,
   отвечаем `y`, получаем **50412**.
2. Тот же вопрос с ответом `N`: модель получает `Отказано: ...`, переходит на `python_eval`
   и получает тот же ответ.
3. `--mode auto` против `--mode strict` на задаче 1: в `auto` скрипт выполняется без вопроса,
   в `strict` модель получает отказ и считает через `python_eval`.
4. Таймаут без модели:
   `uv run python -c "from agent import tools; print(tools.call('python_eval', '{\"expression\": \"sum(range(10**12))\"}'))"`
   Через 5 с приходит `Ошибка TimeoutError`.
5. Эксплойт из пункта 1 показать тестами: `uv run --group dev pytest -k denied -v`.

### 6. Пределы защиты и итоги (10 мин)
- Показать обход ворот 1 (упражнение 3):
  ```python
  from sympy import sympify
  u = chr(95) * 2
  print(sympify(u + "import" + u + "('os').getcwd()"))
  ```
  Скрипт проходит AST-проверку и выполняется, если человек ответит `y`.
  Вывод: **поэтому `python_run` спрашивает всегда**. Защита строится в несколько
  слоёв (deny → человек → песочница), и ни один слой не идеален.
- Что дальше:
  - проверка вписана в цикл, логирование и аудит придётся добавлять туда же → хуки (s04);
  - «всегда» живёт в памяти процесса → постоянные правила понадобятся в **занятии 4** (банк задач, запись на диск);
  - модель может бесконечно получать отказы → лимит шагов (**занятие 8**).
